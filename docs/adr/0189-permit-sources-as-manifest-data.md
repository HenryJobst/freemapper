# ADR 0189: Permit sources as manifest data

Date: 2026-11-23

Status: Accepted

Refs: issue #273, ADR 0130, ADR 0146, ADR 0188.

## Context

The WFS services behind the permit notes (protected areas, monuments, water, forest) were Rust tables: key, label, credit, address, output format and, per layer, a reading with the names of its attributes. Every moved service needed a release, and a folder adapter (ADR 0188) could not reach them. About 220 addresses sit in code; the tables are the largest share.

## Decision

A manifest declares such a source as `[[permits.wfs]]` (format 1, `docs/adapters/manifest-v1.en.md`). The validator checks it like every other table: https on a host of `[net] hosts`, no query, lengths, names, the sections and kinds the program knows, and the keys that belong to each of the six readings (`water`, `function`, `unit`, `state-forest`, `object`, `monument`). The declaration is plain owned data (`DeclaredWfs`, adapter-api). The adapter crate that reads the services registers a `PermitSourceFactory` with the registry, as it registers its raster backends; the manifest adapter asks it for the sources, and a program without one answers `manifest.backend-missing`. The factory keeps the texts for the rest of the run (a manifest holds at most 64 KiB, an adapter is made once), so the tables keep their types.

A built-in state takes the sources of its manifest after those its code brings. The first to move are the protected objects of Hamburg; a test holds them to what the table in the code gave: the same facts, the same requests and the same findings. The other tables follow state by state, one pull request each (issue #273, stage 2b); the protected objects of Saarland, the smallest table without constants of its own, came second, those of Brandenburg third and the biotopes of Berlin fourth and those of Hesse fifth and those of North Rhine-Westphalia sixth and those of Schleswig-Holstein seventh (its note of gaps may be up to 400 characters long), those of Baden-Württemberg eighth and those of Rhineland-Palatinate ninth and those of Saxony-Anhalt tenth and those of Bavaria eleventh and those of Saxony twelfth; the monuments of seven states (Hesse, Baden-Württemberg, Bremen, Saxony, Brandenburg, Rhineland-Palatinate, North Rhine-Westphalia) followed in one pull request, each held to its table by a test, and the module `denkmal_permits` is gone. The remaining sources of Saarland (Reviere, protection areas, Baudenkmale), Hesse (water protection areas) and Schleswig-Holstein (state forest, Naturwald, water protection areas) followed; their fixture tests now read through the declared tables, and the module `state_permits` keeps only those tests. The manifest sources of Schleswig-Holstein now come after its monuments from the code, so the order of its notes changes by one place. Hamburg followed with its six services and with three additions to the schema: the readings `district` (with the source key `offices`, which names the offices of the city state's districts) and `green-space` (a name with a fallback and a district given as a number into a list), and `administration_attribute` on a `unit`, so that the administration can be named by the feature ("Bezirksamt Altona"). The module `lgv_permits` keeps only its fixture tests, which now read through the declared tables. Brandenburg's Reviere and forest functions and Baden-Württemberg's water protection zones followed in one pull request; they add to the readings the key pair `unit_attribute` and `unit_prefix` on a `unit` (a Revier within an Oberförsterei), `authority`, `planned_label` and `name_form = "register"` on `water`, and the source key `note`. A zone is now "provisional" when the attribute holds exactly the value `planned_value`; the code had tested its start. The shapefile of Brandenburg's water protection areas stays in the code until the manifest has a table for shapefiles. Berlin's seven services followed, the last WFS tables in the code. They add the readings `playground` and `owner` (an attribute and a list of the owners that come with their name), `dedication` and `name_form = "park"` on a `green-space` (whose district may also be a plain name), `point_names` on an `object` (a point takes its name from the first of several attributes) and a note of up to 600 characters. A monument of Berlin without a kind now takes the fixed kind `Denkmal`; the code had left it out. The module `berlin_permits` keeps the geometry the generic reader shares, and its fixture tests. The shapefiles followed: the manifest has a second table, `[[permits.shapefile]]`, with the keys of a service source but a zip as `url`, a `crs` and exactly one layer without a feature type; the validator reads both tables into one list (the services first, together at most twelve), the declaration carries `shapefile: true`, and the factory makes a `ShapeTableSource` of it. North Rhine-Westphalia's Forstbetriebsbezirke, Staatswald and water protection areas, Brandenburg's water protection areas and the service LINFOS moved; the naming of an office (a Regionalforstamt unless the name says Forstamt, the Arnsberger Wald as Lehr- und Versuchsforstamt) is data now: `office_unless` and `office_exceptions` on a `unit` and a `state-forest`. A name written in capitals now comes out in the case of a name there too; the code had taken the text as it was. A feature type of a permit layer may hold letters beyond ASCII (`ps:Flächennaturdenkmale`); the request writes them percent-encoded. The address of a permit service may carry a fixed query of plain `name=value` pairs that selects the service on the server (`?mapfile=glb`); `adapters probe` appends its question to it. The two WMS of Saxony that the program asks at points (ADR 0139, the Reviere and the forest functions of the Sachsenforst) are the table `[[permits.getfeatureinfo]]`: a source without `url` whose layers name their own service (`url`, `wms_layers`, `one`) and have no feature type; the declaration carries `getfeatureinfo: true` and the factory makes a `GfiSource` of it, which keeps of a feature the attributes its reading names. The functions are told by a code, which the new reading `function-code` takes from data (the codes of the three functions, the codes of a zone of a drinking water protection area as a prefix and a length), and the office of the national park, whose name the Reviere cut at 40 characters, is data too (`office_renames`). The source of Saxony comes last among its manifest sources now, as the tables are read in the order of services, shapefiles and points; the module `sbs_permits` keeps only its fixture tests. The list of monuments of Schleswig-Holstein followed, one GeoJSON file for the state (about 52 MB): the manifest has a fourth table, `[[permits.geojson]]`, with the keys of a shapefile source but a file as `url`, a `crs` and exactly one layer without a feature type; the declaration carries `geojson: true` and the factory makes a `GeoJsonSource` of it, which keeps the file in the shared cache (at most 150 MB) and cuts it to the map box. The source of Schleswig-Holstein comes last among its manifest sources now, as the tables are read in the order of services, shapefiles, files and points; the module `ldsh_permits` keeps only its fixture tests, which now read through the declared table. The Naturdenkmale and geschützte Landschaftsbestandteile of Lower Saxony followed, read from the NLWKN's ArcGIS REST map service (ADR 0148): the fifth table, `[[permits.arcgis]]`, has the keys of a WFS source, but `url` is the map service, a layer's `type_name` is its number in it (one to four digits) and the answers are always WGS 84, so it has no `output_format`, `gml`, `crs`, `native_crs` or `offices`; the declaration carries `arcgis: true` and the factory makes the table source of `arcgis_permits` of it. The tables are read in the order of services, shapefiles, files, ArcGIS services and points; the module `natur_permits` keeps only its tests, which now read through the declared table.

## Consequences

- A moved permit service of a migrated state is corrected in a folder (ADR 0188) without a release, and `adapters probe` (ADR 0185) reads its address from the manifest.
- The notes read the same. The order of the sources of a state is that of the code, then that of the manifest.
- A manifest that declares a source needs freemapper 0.28.0 or later; `min_freemapper` says so.
- The 64-URL limit of a manifest may need to grow when large states move their tables.

## Addendum: the addresses of the point clouds (issue #273, stage 2)

The point clouds of Brandenburg, Berlin, North Rhine-Westphalia, Rhineland-Palatinate, Saarland and Bavaria have their addresses in the manifest, in the table `[point_cloud]`: a `kind` (`laz-tiles`, `index-json`, `meta4`, `currency-csv`, `zip-archives`), the folder `url` and, for the three kinds that read an index, an `index_url`. The backend keeps what is code: the names of the tiles, the table of archives, the classes left out, the megabytes per tile and how it reads the index. A table that names more would only move code into data that no one could change without the code. The built-in adapter makes its backend from the table when it is made; the constants of the backends are test tools (`feature = "testing"`) that hold each manifest to the old addresses. A folder adapter that replaces a built-in state keeps no point cloud, since its backend is code and the manifest of a folder names none.

## Addendum: the address of the orthophoto WMS (issue #273, stage 2)

The orthophoto WMS of nine states (Saxony, Hesse, Rhineland-Palatinate, Baden-Württemberg, Schleswig-Holstein, Saarland, North Rhine-Westphalia, Bavaria, Lower Saxony) is in the manifest: `[orthophoto]` of a backend takes `url`, `layer` and `max_px`, each optional. The registry holds a factory for these backends instead of a finished backend; the manifest adapter calls it with the keys the table states, and the factory fills each key the table leaves out from the built-in manifest of the state. A folder that replaces a state (ADR 0188) therefore changes only what moved, and one without the keys runs as before. The CRS, the info layer and the reading of the answers stay in the backend, with the tile and download addresses of the terrain and surface models: those are code that no address alone moves. The old constants are test tools, and a test holds each manifest to them; the provider and the cache folder of each backend are fixed by a test, so that no cache of a person is orphaned. Brandenburg, Berlin, Hamburg, Mecklenburg-Vorpommern and Bremen follow in a later change, because their backends build the request in code (Hamburg's year, a tile mask, a function for the layers).

## Addendum: the other addresses of the raster backends (issue #273, stage 2)

The tile lists, archives, WCS, STAC APIs and file servers of five states are in the manifest too: `[orthophoto]` of a backend takes a table `endpoints`, names mapped to https addresses without a query. Which names a backend asks is a table in the manifest crate (`TAKES_ENDPOINTS`): `lgv` (`metadata`, `dgm1`, `bdom`), `geobasis-nrw` (`hm`), `lgln` (`dop-stac`, `dgm-stac`, `dom-stac`, `dgm-wcs`, `dom-wcs`), `laiv-mv` (`overview`, `dop-wcs`, `dgm-wcs`, `dom-wcs`) and `geobremen` (`wms`, `files`); Hamburg also takes `url`, `layer` and `max_px` of its WMS. The config of a table (`RasterConfig`) holds the names, and a name left out comes from the built-in manifest, as for the WMS. The registry factories build the backends from the merged config. The code of each backend keeps what it does with the addresses: the coverages and extents, the tile masks of the Downloadportal, the pinned vintage of Hamburg's WMS and the layers Bremen reads from its capabilities. The old constants are test tools, and a test holds each manifest to them; one test per backend asks it for its services at addresses of the test and fails on a request elsewhere. The download estimate still looks into the cache folders of the built-in addresses. The tile providers of Brandenburg and Berlin stay in the code: their addresses are built by a function of the product that is shared with Saxony's tile index, and a change there would reach more than this stage.

## Addendum: the tiles of Brandenburg and Berlin (issue #273, stage 2)

The tile providers of Brandenburg and Berlin are in the manifest too: `[orthophoto.endpoints]` of the backend `lgb` names `data` (the folder of the archives of the orthophoto, the DGM and the bDOM and of the nDOM point clouds) and `currency` (the folder of the currency CSV lists). The code keeps what lies below: the folders of each product, the names of the files and how the lists are read. The tile fetch takes the addresses as an argument (`fetch_tiles_at`, `fetch_tiles_each_at`, `fetch_ndsm_tiles_at`); the functions without `_at` and the `tile_url` and `currency_csv_url` of the products ask the built-in manifest, so that tests and Saxony, whose share tokens come from the tile index, run as before. The old constants are gone, and tests hold both manifests to the old addresses. One test per fetch asks a fetcher that holds only the addresses of the test and fails on a request elsewhere. The backend `lgb` has no WMS, so it takes `endpoints` only. Saxony's tile addresses stay in the code.

## Addendum: the height models of Baden-Württemberg, Saarland and Rhineland-Palatinate (issue #273, stage 2)

The archives and tile lists of three more height-model backends are in the manifest: `[orthophoto.endpoints]` of `lgl-bw` names `flights` (the WFS with the flight of each orthophoto tile) and `files` (the file server of the DGM1 and nDOM1 archives), that of `lvgl` names `share` (the open-data share of the DGM1 and DOM1 archives) and that of `lvermgeo-rp` names `tile-list` (the Blattschnitt WFS) and `data` (the file server of the tiles and their Metalinks). They are in `TAKES_ENDPOINTS` and follow the rules of the first addendum. The old constants are test tools; `the_endpoints_of_each_manifest_are_the_ones_the_code_held` holds each manifest to them. Hesse, Schleswig-Holstein, Saxony (and the Saxon tiles Brandenburg reads), Bavaria and Saxony-Anhalt keep their addresses in code for now: their download clients carry the addresses through many more functions, and Bavaria's file server is also the address of its LoD2 buildings.
